# Проверка сервиса

Табличный отчёт проверяется через настоящий GET
`/api/v1/comparisons/{job_id}/report`: PDF с кириллицей, полным текстом многостраничной
строки, уникальными фактами, статусами/источниками ИИ, правами владельца и Telegram-читателя,
отказом чужой сессии и TTL. Проверяется отсутствие вызовов OCR, VLM и очереди.
Типы «Оформление» и «Структура таблицы» исключаются из строк и статистики отчёта
при любом источнике/статусе, в том числе когда других событий нет. Основной результат сохраняется.
Параметр `show_unverified` отчёта повторяет положение переключателя: скрываются все
непроверенные события, включая неоднозначности и гипотезы ИИ. Проверяются повторное
включение, выбор до запуска, доступ через Telegram и сохранение исходных статусов/счётчиков.
Chrome проверяет новую кнопку под списком на одной линии с PDF, скачивание и сброс,
а также скачивание отчёта по открытой Telegram-ссылке.
Счётчик непроверенных областей сохраняет правило интерфейса: считаются уникальные
причины покрытия. Несколько локальных строк могут относиться к одной такой области;
они сохраняются в отчёте с полными текстами и реальными статусами.

Регрессии `tests/regression/test_comparison_exclusions.py` проверяют все пары
`-`, `—`, `–`, их эквивалентность внутри слов, предложений, дат и числовых выражений,
соседние реальные изменения, исходные диапазоны, разбитые OCR-токены и низкую
уверенность знаков. Сохраняется неопределённость ненадёжного содержательного текста.
Проверяются разные разделы, повторяющиеся тире, независимые группы, неверный синтаксис,
замены разной длины, UTF-8/BOM и восстановление старых снимков результата.

`test_ocr_recheck.py` проверяет три исхода локальной проверки, отдельный синтаксис
`ocr:`, русский контекст, защиту идентификаторов, нативные страницы смешанного PDF,
сохранение отрицаний и чисел, правильные причины и отсутствие дублей после VLM.
Интеграционный тест перечитывает настоящие растровые строки «не»/«т» и проверяет
серую редактируемую DOCX-разметку; совпадение не даёт заливки. При `--real-documents`
отдельно проверяются реальные файлы `examples/`, пункты 1.2 и 10.2, сохранение аванса
`70% → 50%` и SHA256 исходников. Файлы и диагностические результаты остаются вне Git.
Исключения не создают адресных ИИ-целей; страничный ответ ИИ не возвращает уже
разрешённую пару как новое изменение. Правки файла и пустой список проверяются
через настоящую сборку settings/use-case. Настоящий DOCX сравнивается с растровым PDF
через LibreOffice и Tesseract. HTTP-тесты проверяют отсутствие ложных строк в PDF-отчёте
и выдаче UI. Браузер и API проверяют, что категория «Непроверенные области» и статус
«Не проверено» включают все активные неопределённости, а скрытие не меняет счётчики.
Функциональные проверки запуска
охватывают отказ основного образа, успех зеркала, отказ обоих путей и отсутствие
повтора при ошибке тестов, в том числе с `--log`.

Windows: `uv sync --frozen`, затем `./ops/check-quality.ps1` и `./ops/test.ps1`.
Linux с Docker: `bash scripts/test.sh`; сборка и тесты видны в терминале.
Ruff/format/архитектура на Linux: `bash scripts/check-quality.sh`.
Проверки не создают коммиты и не выполняют push.
Для явного сохранения подробностей передайте `--log`: файлы
`.cache/tests-linux.log` и `.cache/quality-linux.log`. Windows-проверки продолжают
сохранять подробные логи в `.cache/`.

На Windows нужны Python 3.12+, uv и Node.js; для полного прогона — Git Bash,
Chrome/Chromium, LibreOffice и Tesseract с языками rus+eng.
Если политика PowerShell блокирует локальные сценарии, используйте
`powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1`
и аналогично `-File .\ops\test.ps1 -RealDocuments`; системная политика не меняется.

Наборы: unit (алгоритмы, нормализация), regression (проценты, отрицания, вставки,
перемещения, отказ второго OCR), functional (HTTP→use-case→SQLite→доступ/TTL),
security (архивы, внешние ресурсы, парольные PDF, квоты), architecture (импорты,
документация, Settings, frontend), integration (реальные PDF/OCR/LibreOffice,
девять пар форматов, CropBox/Rotate, 300 страниц, экспорт), browser (Playwright),
frontend (чистые JS-правила через Node test).

Подготовка RabbitMQ проверяется функциональными тестами через настоящий Bash и
временную подмену команды Docker: первый и повторный запуск, исправление прав,
неверный пароль, ошибки CLI/сети/контейнера, административная или чужая учётная
запись. Проверяется точная передача спецсимволов через stdin и отсутствие секрета
в аргументах и выводе, включая запуск с `bash -x`. Это проверка сценария запуска;
она не заменяет подключение к настоящему корпоративному брокеру.
Подмена подключается как функция через `BASH_ENV`: Bash и Python читают временные
файлы без их прямого исполнения. Это работает с Docker tmpfs `/tmp`, где действует
`noexec`. Изменять параметры монтирования или устанавливать Docker CLI в test-образ
для этих проверок не требуется. Каждый сценарий проверяет журнал вызовов подмены,
чтобы ранний отказ фикстуры не выдавался за проверку ожидаемой ошибки.
Проверяются также блокировка параллельного запуска, видимость вывода по умолчанию,
явный `--log`, сохранение кода ошибки и ограничение зависшего клиента.

Настоящий RabbitMQ 4.1 проверяется отдельно:

```bash
uv run --frozen pytest -q -m external tests/integration/test_broker_bootstrap.py
```

Нужны доступный Docker daemon и локальный образ `rabbitmq:4.1-management`.
Тест создаёт одноразовый контейнер без портов и сети, затем удаляет его. Проверяются
создание пользователя с точным паролем, повторный запуск, отказ неверного пароля
и удаление временного файла секрета. Compose и проверка shared-сети подменяются;
команды RabbitMQ выполняются настоящим CLI. Общий production-брокер этим тестом
не изменяется и его доступность не подтверждается.

Windows-скрипт декодирует вывод Node как UTF-8 и использует TAP-отчёт. Поэтому
русские названия тестов и итоговые счётчики корректно читаются в PowerShell 5.

В CI и контейнере используются только синтетические обезличенные документы,
создаваемые `tests/factories.py`. Отсутствие инструментов на Windows отмечается
как skip, а не как прошедшая интеграция. Browser-тесты используют отдельный профиль
Chrome/Chromium и локальную ограниченную тестовую доставку вместо RabbitMQ;
подключение production-брокера этим не подтверждается.

Реальные оригиналы находятся в игнорируемом `examples/`. Эталонная матрица
`examples/golden-matrix.json` ведётся независимо от тестируемого алгоритма.
Нельзя исправлять ожидаемые значения по ответу алгоритма. Коррекция допустима
только после повторной проверки оригинала и записи основания. В частности,
автоматическая нумерация проверяется по Word-рендеру, а не только по `w:t`.
Матрица обязана явно сообщать, когда проверка не исчерпывающая.

Для реальных данных сохраняйте SHA256 исходников, версии инструментов, фактическое
время прогона, найденные значения и области обеих сторон. Сверяйте каждую запись,
отрицательные контроли, false positive, false negative и unverified отдельно.
Один общий similarity score или количество различий не являются приёмкой.

Ручная проверка:

1. Открыть `http://192.168.55.3:8082`, загрузить DOCX слева и скан PDF справа, оставить ИИ выключенным.
2. Увидеть настоящие этапы обработки и два изображения документов.
3. Проверить п. 2.2: 70% → 50%, п. 5.2: предел 5% → 0,01%; дневная ставка не меняется.
4. В п. 4.3.1 цифра 70% одинакова; словесное значение может отличаться.
5. Проверить адрес, счёт поставщика, две печати/подписи и все непроверенные области.
6. Выбрать отличие: обе панели должны перейти к соответствующим местам.
7. Проверить фильтры, поиск, страницы, масштаб, поворот и переключатель связи.
8. Скачать оба PDF, открыть и сверить серую подсветку с реальным изменением.
9. Для каждого DOC/DOCX скачать обе версии: PDF и редактируемый DOCX.
   DOCX содержит только серые подтверждённые изменения и не зависит от переключателя;
   пропуски отдельных заливок указаны под кнопкой, скачивание остальных сохраняется.
10. Проверить сброс/отмену, удаление и недоступность результата после TTL.
11. Выполнить четыре комбинации двух режимов ИИ; алгоритмы должны работать всегда.
12. Наблюдать отдельные счётчики режимов и пакет 2 и далее; открыть «Подробнее».
13. Выключить показ непроверенных областей: убрать их из списка, деталей и обеих подсветок;
    счётчик непроверенных не меняется, подтверждённые изменения остаются.
14. Скачать обе стороны с выключенным и включённым показом. В PDF соответствуют
    оранжевые рамки; подтверждённые серые/зелёные изменения сохраняются независимо от источника.
15. При частичном отказе повторить незавершённые операции без загрузки, OCR и потери успехов.
    При недоступном ИИ основной результат сохраняется; после завершения доступны актуальные PDF.

Новые проверки охватывают 25 целей (включая 13/24/25), ограничение конкуренции,
429/503 и сетевые отказы, пустой/обрезанный JSON, отклонение схемы/флага reasoning,
сохранение частичных результатов, время, отмену, возобновление и дедупликацию.
Отдельно проверяются повторяющиеся числа, разные колонки сторон договора,
недостаточная OCR-уверенность, разделение больших изображений, целые абзацы
на границах полос и вставленная страница. Геометрия Word восстанавливается
только по уникальной точной цитате готового рендера; повторяющийся MP не угадывается.
Оба варианта PDF проверяются с прежними цветами и переключателем; единственный
DOCX — с серой подтверждённой разметкой и неизменным исходным содержимым.
Browser-набор включает пять сценариев
режимов (четыре комбинации и частичный отказ с повтором).

Визуальное принятие дополнительно проверяется без `result.matches`, при ошибке OCR,
перестановке колонок, нехватке геометрии, частичном покрытии родителя, добавлении/
удалении с реальным якорем и конфликте чисел. Проверка 30 + 5 − 2 = 33 исключает
повторный подсчёт известных фактов. Поля и внутренние ссылки Word остаются
отдельными `unsupported_property`. Промежуточный checkpoint обновляет PDF,
а DOCX формируется отдельно с проверкой исходного OOXML-пакета.

`tests/functional/test_word_downloads.py` проходит все девять пар через настоящий
HTTP и worker-use-case с реальными адаптерами. Для каждого Word проверяются PDF
и DOCX одновременно, для PDF — отсутствие Word-кнопки/артефакта. Принудительные
ошибки форматов не блокируют друг друга. `tests/regression/test_word_export.py`
проверяет сложные runs, табуляцию, таблицы, стили, сохранность вложений,
подтверждённый ИИ, неоднозначные якоря, счётчики пропусков и отсутствие PDF-гейта.

`tests/functional/test_telegram_integration.py` проверяет все четыре режима,
сохранение old/new, авторизацию до чтения тела, конкурентные идемпотентные отправки
и активации билета, безопасные ошибки/лимиты, TTL, ротацию и права чтения.
Отдельный browser-сценарий открывает результат в новом профиле, очищает fragment,
скачивает обе стороны и проверяет повторное открытие с ограниченной cookie.
Контракт оператора и разработчика бота: [TELEGRAM_INTEGRATION.md](TELEGRAM_INTEGRATION.md).

Внешняя runtime-интеграция `tests/integration/test_worker_runtime.py` требует
тестовый образ от `bash scripts/test.sh` и локальный `rabbitmq:4.1-management`.
Она запускает одноразовый изолированный тестовый брокер без портов, проверяет
`healthy`, настоящее фоновое сравнение и JSON timing-события, затем удаляет контейнеры.
Это не дополнительный production RabbitMQ. Отдельный запуск:
`uv run --frozen pytest -q -m external tests/integration/test_worker_runtime.py`.
Необходимость локального образа не подменяется успешным mock-тестом: отсутствие
предпосылок отмечается как skip. Реальная проверка shared-vlm описана в локальном
отчёте и [сводке результатов](validation.md).


## Разная пагинация, фильтры и новая приватная матрица

`tests/integration/test_advertising_contract.py --real-documents` использует
только локальные `examples/old.docx`, `new.pdf`, `expected_matrix.json`.
Проверяются 6/4 страницы, все 41 содержательный сценарий по пункту, стороне
и ожидаемым изменённым словам, 15 контролей, оба платежа 50% → 70% / 50% → 30%,
отсутствие ложного добавления/удаления реквизитов, служебной графики ЭДО,
переход 6 → 4 и настоящие PDF/DOCX-экспорты. Краткие формулировки матрицы
являются смысловыми сценариями, а не эталоном количества атомарных событий.
Приватные артефакты сохраняются только в `.cache/advertising-verified`.
Хеши исходников и прежних эталонов контролируются без их изменения.
Предыдущие реальные тесты выбирают исходную пару поставки явно, чтобы новые
примеры не подменили её при поиске через glob.

Синтетические регрессии проверяют отмену оформления во всех форматах,
переносы и группы абзацев, возврат диапазонов Word, одинаковое число в другом
пункте, назначение банковского поля, сохранение сомнительности внутри группы.
Browser проверяет множественный выбор, сброс, состав скачанного отчёта,
оба направления синхронизации добавлений/удалений и отключение связи.
HTTP-тесты продолжают проверять владельца, Telegram-доступ и TTL отчёта.

Ручная проверка: открыть `http://192.168.55.3:8082`, сравнить новую пару
в правильном порядке. Выбрать несколько категорий и скачать отчёт: строки
и его статистика должны соответствовать фильтру и положению переключателя
непроверенных областей. Общая статистика задания не меняется. Для удаления
из старого п. 8.5 переход должен вести со старой страницы 6 на новую 4 при
включённой связи. При выключенной связи отсутствующая сторона остаётся
на выбранной вручную странице. PDF и DOCX скачиваются прежними кнопками.


`tests/integration/test_storage.py` проверяет настоящий конкурентный доступ четырёх
читателей и одного автора checkpoint, временную блокировку чтения/переименования
и ограниченный отказ при постоянном запрете. Эта регрессия обнаружена полным
Windows-прогоном во время повторной ИИ-проверки; чтение не должно обрывать polling.
Новая приватная пара отдельно проверяется через настоящий browser/worker: 6 → 4,
Word-кнопки и отчёт с выбранными категориями.


## Преамбула и переход при добавлении

В локальную `examples/expected_matrix.json` добавлены C14/C15: отсутствие ложных
событий на общем тексте и сопоставление при объединении с изменённым абзацем.
41 содержательный сценарий и прежние 13 контролей сохранены. Проверяются реальные
диапазоны обеих сторон, отсутствие ложной строки в отчёте, неизменная заливка
общей преамбулы в DOCX и соответствие страниц всех добавлений/удалений.
`examples/` остаётся вне Git: обновлённую приватную матрицу нужно переносить
между машинами вместе с исходной парой; `golden-matrix.json` не менялся.

Синтетические регрессии проверяют оба направления split/merge, дробление на OCR-блоки,
реальное новое обязательство и копию той же фразы в другом разделе. Браузер намеренно
задерживает изображение выбранной стороны: обе панели должны перейти 6 ↔ 4 до его
загрузки. Также проверяются выключенная связь и реальная вставка п. 6.3: старый 4 ↔ новый 3.
Ручная проверка: сравнить `old.docx → new.pdf`, выбрать добавление п. 6.3, затем удаление
п. 8.5; отключить ↔ и проверить независимость панелей. Общая преамбула должна отсутствовать
в различиях и скачанном отчёте. Остальные изменения и обычные PDF/DOCX остаются доступны.
