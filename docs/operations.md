# Эксплуатация

Нужны Docker Engine с Compose v2.24+, GNU coreutils (`timeout`), util-linux (`flock`),
существующий RabbitMQ и сеть `ai-shared`.
Собственный брокер, Redis или модель в этот проект не добавляются.
Клиенты используют `rabbitmq:5672` и `http://shared-vlm:8000/v1`, модель `shared-vlm`.
Команды выполняются из каталога `~/projects/contract-diff-search`, где находятся
`.env.example`, `compose.yaml` и `scripts/`, а не из родительского `~/projects`.
Физическая модель, GPU и инфраструктура принадлежат shared-infrastructure.

Первый запуск после заполнения единственного обязательного секрета в `.env`:

```bash
bash scripts/up.sh
```

Для внешнего бота дополнительно нужен `TELEGRAM_INTEGRATION_TOKEN` в `.env`;
без него только интеграционные методы возвращают 503, браузер продолжает работать.
Пользовательский адрес `PUBLIC_BASE_URL` задаётся отдельно в baseline, по умолчанию
для согласованной LAN это `http://192.168.55.3:8082`. Безопасное создание/ротация
секрета и полный контракт описаны в [Telegram-интеграции](TELEGRAM_INTEGRATION.md).
Общие RabbitMQ/VLM и их параметры для этого не меняются.

Сборка выводится в терминал. Перед каждым этапом показываются его название,
текущее время и число секунд с начала запуска. Повторный одновременный `up.sh`
останавливается на блокировке `flock`, вместо создания ещё одного bootstrap-процесса.
Если подробности нужны только в файле, явно передайте `bash scripts/up.sh --log`:
они сохранятся в `.cache/deploy.log`, а этапы останутся видны.

Скрипт собирает образ приложения, читает конфигурацию через Pydantic Settings
в одноразовом процессе этого образа и проверяет работающий `shared-rabbitmq-1`
в сети `ai-shared`. Отсутствующие пользователь и vhost `contract-diff` создаются
через `docker exec … rabbitmqctl`; права `.* / .* / .*` действуют только внутри
выделенного vhost. Уже настроенные сущности повторно не создаются.
Брокер не запускается, не пересобирается и не перезапускается.

Пароль передаётся через stdin в закрытый временный файл с правами `600` в RAM
(`/dev/shm`) внутри существующего брокера. CLI выполняет постоянное RPC-выражение,
которое читает этот файл: интерактивное чтение stdin Erlang не используется.
В аргументах процессов и логах пароля нет; файл удаляется через `trap`, в том числе
при штатном отказе и ограничении времени. Xtrace отключён до чтения секрета.
Административный пароль
`shared_admin` не нужен: CLI использует локальный Erlang cookie существующего
контейнера. Runtime приложения использует только выделенного пользователя.
Существующий пароль не меняется автоматически. При несовпадении исправьте
`RABBITMQ_PASSWORD` в `.env` либо выполните согласованную ротацию отдельно.
Скрипт отклоняет runtime-пользователя со служебными тегами или доступом к другим
vhost, не изменяя чужие настройки. Ошибка чтения состояния брокера останавливает
запуск до старта API/worker.

`RABBITMQ_CLI_TIMEOUT_SECONDS=30` читается через Pydantic из `.env.example`.
Это предел всего процесса CLI внутри контейнера, включая старт Erlang и ожидание,
с принудительным завершением через дополнительные 3 секунды. Для передачи секрета
есть отдельный предел оболочки с запасом на уборку. Docker-клиент при работе с RabbitMQ ограничен
45 секундами плюс 5 секунд до принудительного завершения при стандартном значении.
Один только `rabbitmqctl --timeout` ограничивает RPC и не заменяет эти пределы.

Для проверки состояния корректные команды RabbitMQ 4.1:

```bash
docker exec shared-rabbitmq-1 rabbitmqctl list_users
docker exec shared-rabbitmq-1 rabbitmqctl list_vhosts name
docker exec shared-rabbitmq-1 rabbitmqctl list_permissions -p contract-diff
```

`list_users` не принимает колонки `name tags`.
CLI использует cookie существующего брокера; общие административные credentials
в настройки приложения не добавляются.

Обновление на Linux после проверки и push с Windows:

```bash
git pull --ff-only origin main
bash scripts/test.sh
bash scripts/up.sh
docker compose --env-file .env.example --env-file .env ps
curl --fail http://192.168.55.3:8082/readyz
```

Публикация для LAN — `192.168.55.3:8082`: откройте этот адрес с компьютера в той же
сети. `192.168.55.3:8080` относится к другому сервису. Адрес и порт задаются обычными
параметрами `APP_BIND_IP` и `APP_PORT` в `.env.example`; `.env` содержит только секреты.
Приложение внутри контейнера слушает `APP_HOST=0.0.0.0`. Проверка через
`127.0.0.1:8082` на хосте не подходит при публикации только на указанном LAN-IP.
Для локального Docker на машине без адреса `192.168.55.3` переопределите
`APP_BIND_IP=127.0.0.1` окружением команды. Если порт занят или такого IP нет на
сервере, Docker покажет ошибку публикации; не меняйте порты соседних сервисов.

Сборка и тесты также видны при `bash scripts/test.sh`, проверки качества — при
`bash scripts/check-quality.sh`. Явный `--log` переключает подробности в
`.cache/tests-linux.log` или `.cache/quality-linux.log`; ненулевой код сохраняется.

Одноразовая уборка процессов, оставшихся от старого зависшего скрипта:

1. В терминалах со старым `bash scripts/up.sh` нажмите `Ctrl+C`.
2. Выполните `docker top shared-rabbitmq-1 -eo pid,etime,args`. Это список только
   процессов данного контейнера с PID хоста.
3. Найдите строки старого `rabbitmqctl`, завершающиеся на
   `--quiet --timeout 30 add_user contract-diff`. Проверьте полный аргумент и время
   работы. У этого вызова могут остаться и оболочка, и дочерний Erlang-процесс.
4. Для уборки именно старой формы команды выполните приведённый ниже цикл. Он
   работает только внутри указанного контейнера, проверяет префикс CLI и точный
   конец старого вызова `add_user contract-diff`, затем посылает TERM. PID основного
   broker и CLI других приложений не подходят под оба условия.
5. Снова выполните `docker top …`, затем запускайте обновлённый `bash scripts/up.sh`.

```bash
docker exec shared-rabbitmq-1 sh -c '
for entry in /proc/[0-9]*/cmdline; do
  [ -r "$entry" ] || continue
  cmd=$(tr "\000" " " < "$entry") || continue
  case "$cmd" in
    "/bin/sh /opt/rabbitmq/sbin/rabbitmqctl "*|"/opt/rabbitmq/escript/rabbitmqctl "*)
      case "$cmd" in
        *" --quiet --timeout 30 add_user contract-diff ")
          pid=${entry#/proc/}
          pid=${pid%/cmdline}
          printf "TERM old contract-diff CLI: %s\n" "$pid"
          kill -TERM "$pid" 2>/dev/null || true
          ;;
      esac
      ;;
  esac
done
'
```

Командная строка самого cleanup-shell начинается с `sh -c`, поэтому не проходит
проверку CLI-префикса. Перед запуском убедитесь, что вывод `docker top` соответствует
описанной старой форме. Для нестандартного пути CLI сначала разберите свежий вывод
и завершайте только отдельно проверенные PID; не расширяйте шаблон до всех Erlang-процессов.

Не используйте общий `pkill -f rabbitmq` и не перезапускайте shared-брокер ради
уборки старых CLI. Если PID из предыдущего вывода уже исчез, повторно проверьте
список: сохранённые числовые PID могли быть переиспользованы.

Если `.env` отсутствует и секрет передан окружением процесса, уберите второй
`--env-file .env` в прямых Compose-командах. Скрипты учитывают это автоматически.
Не выполняйте `down -v`: том содержит ещё не истёкшие текущие результаты.
Остановка проекта не должна останавливать общие сервисы.

Диагностика:

```bash
docker compose --env-file .env.example --env-file .env logs --tail=100 api worker
docker compose --env-file .env.example --env-file .env ps
```

`/healthz` — живой HTTP-процесс. `/readyz` — инструменты и обязательная очередь;
доступность VLM не определяет готовность основного сравнения.
У контейнеров ограничены память, CPU, процессы, временный диск; пользователь
непривилегированный, root filesystem read-only. Docker ротирует stdout/stderr.
Предельная распаковка и XML проверяются до обработки. Каталоги Word-профилей
изолированы; запуск subprocess без shell, с таймаутом и завершением дерева при отмене.

Для внешнего HTTPS reverse proxy задайте `COOKIE_SECURE=true`, реальное приложение
публикуйте только в доверенной корпоративной сети/VPN. Не передавайте capability
в URL, не расширяйте CORS. API требует HttpOnly cookie и `X-Requested-With: ContractDiff`
для изменяющих запросов. Программный клиент сначала вызывает `GET /api/v1/session`.

TTL начинает отсчёт от завершения/ошибки/отмены; зависшие задачи имеют отдельный
максимальный срок. Уборка работает в API независимо от браузера и доступности брокера,
повторяется после рестарта. API немедленно прекращает доступ по времени, даже до
следующего прохода уборки. Удалённые имена файлов очищаются из tombstone-метаданных.

Значимые операции пишут JSON timing-события без текста договора и credentials.
Отладочные OCR/LibreOffice-файлы лежат только внутри временного каталога задания.
Не публикуйте содержимое `.data`, `.cache`, `examples` и скриншоты реальных договоров.

Колонки режимов ИИ добавляются в существующую SQLite автоматически под блокировкой;
старый `use_ai=true` преобразуется в полный режим. Ручная миграция не требуется. Это временное
хранилище без пользовательской истории; резервное копирование договоров не выполняется.
Откат: вернуть проверенную версию кода и пересобрать только процессы проекта.

ИИ использует два независимых режима и checkpoint; правила описаны в
[ИИ-проверке](ai-review.md). Отказы модели видны отдельно от основного сравнения.
Операционные JSON-события можно посмотреть без доступа к содержимому договоров:

```bash
docker compose --env-file .env.example --env-file .env ps api worker
docker compose --env-file .env.example --env-file .env logs --tail=100 worker
docker compose --env-file .env.example --env-file .env exec -T worker python -m app.worker_health
```

Здоровье worker проверяется адресным pong; HTTP `/readyz` не заменяет эту проверку.
Нативные пулы ограничены до загрузки библиотек (`NATIVE_THREADS=1` и семь
библиотечных переменных). Лимит процессов контейнера не увеличивается.
Успешные операции ИИ повторно не отправляются. При отмене очередь ещё не
запущенных запросов снимается; активные запросы ограничены HTTP-таймаутом.
Старый экспорт во время изменения результата не выдаётся как актуальный.
